# AI Gateway 项目架构设计

## 1. 项目定位

本项目是一个企业级 AI Gateway，面向大模型接入与治理场景，提供统一的模型访问入口和完整的管理后台能力。

项目目标包括：

- 支持组织、项目、成员的多租户管理
- 支持 API Key 的生命周期管理
- 支持多模型供应商统一接入与路由
- 支持鉴权、限流、配额、审计、日志与可观测性
- 提供前后端分离的管理控制台

## 2. 技术选型

### 2.1 前端

- 框架：Vue 3

- UI 组件库：Element Plus

- 包管理器：uv

## 3. 整体架构

项目采用前后端分离架构，建议先以单仓库形式管理，并在后端内部采用模块化单体设计。

### 3.1 仓库结构建议

```text
ai-gateway/
  backend/
  frontend/
  docs/
```

### 3.2 系统结构

系统分为三个核心部分：

1. 管理后台前端
   - 面向管理员和运营人员
   - 提供组织管理、项目管理、Key 管理、模型管理、日志查询等能力

2. 后端管理面 API
   - 面向前端后台
   - 负责系统配置、租户管理、权限管理、审计管理

3. 后端网关面 API
   - 面向业务调用方
   - 提供统一的大模型访问入口
   - 对接多个模型供应商

## 4. 后端架构设计

后端建议采用清晰的分层架构，避免路由、业务、数据访问和外部供应商调用耦合在一起。

### 4.1 分层设计

1. 接口层
   - 提供 HTTP API
   - 处理请求参数、响应格式与异常映射

2. 应用层

3. 领域层
   - 承载核心业务模型与规则

4. 基础设施层

## 5. 网关与模型接入设计

这是项目的核心能力，建议从一开始就建立统一抽象，避免不同模型供应商逻辑散落在业务代码中。

### 5.1 统一网关能力

网关层建议具备以下处理链：

1. 校验 API Key
2. 识别组织与项目
3. 读取项目模型策略
4. 校验模型是否允许调用
5. 校验限流与配额
6. 选择供应商与目标模型
7. 发起实际请求
8. 记录请求日志与 usage
9. 返回统一响应

### 5.2 模型供应商适配器

建议将不同厂商的接入差异封装到 `adapters` 层，包括：

- 鉴权方式差异
- 请求体结构差异
- 流式返回差异
- 错误码映射差异
- Token 统计差异

### 5.3 模型接入与模型出口聚合分层

结合当前需求，建议把模型治理明确拆成“接入侧”和“出口侧”。

#### 接入侧

接入侧负责把单个真实模型节点接进来。

接入侧包含三层：

1. 供应商层
   - 描述厂商或接入源
   - 例如 OpenAI、Azure OpenAI、DeepSeek、自建 vLLM、OCR 服务、文生图服务

2. 接入模型层
   - 描述供应商原始模型
   - 例如某供应商的 `gpt-4o-mini`、`deepseek-chat`、`bge-m3`

3. 节点层
   - 描述实际可调用的接入点
   - 一个接入模型可以挂多个节点
   - 每个节点独立维护地址、权重、健康状态、并发数、token 容量、限流规则

#### 出口侧

出口侧负责将多个接入节点聚合成一个对外服务模型。

出口侧包含两层：

1. 聚合模型层
   - 描述平台对外暴露的统一模型
   - 例如自定义为 `chat-pro`、`embedding-unified`、`ocr-general-v1`
   - 这个名称需要支持自定义

2. 聚合绑定层
   - 描述一个聚合模型绑定哪些接入节点
   - 可绑定不同供应商、不同名称、不同区域的节点
   - 由路由策略决定实际命中哪个节点

这样设计的价值在于：

- 接入管理和出口管理职责分离
- 接入侧只关心“单个节点能不能接进来、能不能稳定运行”
- 出口侧只关心“对外叫什么名字、绑定哪些节点、如何统一服务”
- 调度是按节点进行，而不是按聚合模型名进行
- 同一个聚合模型可以聚合多个不同供应商、不同名称的底层模型节点
- 节点异常时可以快速摘除或切换

### 5.4 统一模型能力分类

需要统一的能力包括：

- 模型元信息
- 模型类别
- 标准请求格式
- 标准响应格式
- 流式输出格式
- 错误码规范
- Token 统计接口
- 成本计算接口
- 健康检查接口

建议将模型能力分类至少定义为：

- `llm`：文本生成、大语言模型
- `vlm`：视觉语言模型，多模态理解
- `embedding`：向量化模型
- `rerank`：重排序模型
- `ocr`：文字识别模型
- `text_to_image`：文生图模型

后续可按需要扩展：

- `speech_to_text`
- `text_to_speech`
- `image_to_image`
- `video_understanding`

### 5.5 节点治理能力

每个模型节点建议具备以下治理字段和运行能力：

- 节点唯一标识
- 节点名称
- 所属供应商
- 所属模型
- 节点接入地址
- 节点状态
- 节点权重
- 最大并发数
- 每秒/每分钟请求上限
- 每分钟/每日 token 上限
- 超时配置
- 熔断状态
- 健康检查状态

网关调度时，建议按如下顺序处理：

1. 根据模型类别选择可用节点集合
2. 过滤禁用节点、异常节点、超限节点
3. 校验节点并发占用
4. 校验节点 token/request 配额
5. 按优先级、权重或最小负载选择目标节点
6. 请求完成后回写节点用量与统计

### 5.6 聚合模型设计

聚合模型是平台对外服务的统一模型视图，建议具备以下属性：

- 聚合模型唯一标识
- 自定义对外模型名称
- 模型类型
- 能力标签
- 描述信息
- 是否启用
- 默认路由策略
- 绑定节点集合

聚合模型需要支持：

- 聚合不同供应商节点
- 聚合不同原始模型名称
- 聚合不同区域或不同部署环境的节点
- 对外统一暴露一个自定义模型名称

网关面对外暴露的 `model` 参数，应始终指向聚合模型名称，而不是供应商原始模型名称。

### 5.7 建议支持的网关接口

建议优先兼容 OpenAI 风格接口，降低调用方接入成本：

- `/v1/chat/completions`
- `/v1/responses`
- `/v1/embeddings`
- `/v1/models`

同时按模型类别预留能力接口：

- `/v1/rerank`
- `/v1/ocr`
- `/v1/images/generations`

## 7. 权限与多租户设计

项目本质上是多租户系统，建议从第一期就围绕组织与项目构建权限模型。

### 7.1 角色建议

- 平台管理员
- 组织管理员
- 项目管理员
- 普通成员
- 只读成员

一期建议进一步收敛成两类实际行为角色：

1. 管理员角色
   - 包括平台管理员、组织管理员、项目管理员
   - 负责项目配置、个人 Key 与项目 Key 配置管理、模型接入配置、聚合模型配置、路由策略配置

2. 普通用户角色
   - 包括普通成员、只读成员
   - 只能登录并查看自己所在或所属项目
   - 可以查看项目关联的聚合模型
   - 可以查看平台级聚合模型
   - 可以查看与自己有权限关联的 API Key
   - 暂不开放 API Key 创建和配置权限

### 7.1.1 聚合模型节点权限管理

在聚合模型和项目策略之间，建议再增加一层“聚合模型节点权限管理”。

这层的职责不是定义路由，而是定义“这个聚合模型可以下发给谁使用”。

建议支持以下授权对象：

- 组织
- 项目
- 个人用户
- 自定义用户组

这样可以实现：

- 平台级聚合模型下发给所有组织
- 某个聚合模型只下发给指定项目
- 某个聚合模型只给特定个人用户可见
- 某个聚合模型按用户组批量授权

建议职责边界如下：

- 聚合模型：定义对外模型名
- 聚合模型节点绑定：定义底层节点池
- 聚合模型节点权限管理：定义授权范围
- 项目模型策略：定义项目级路由覆盖和限流覆盖

### 7.2 权限边界

需要明确以下边界：

- 是否可以查看其他组织数据
- 是否可以创建或删除项目
- 是否可以创建和轮换 API Key
- 是否可以修改模型策略
- 是否可以查看完整调用日志

一期推荐权限边界如下：

- 只有管理员可以创建、编辑、禁用、轮换个人 Key 和项目 Key
- 只有管理员可以创建项目、编辑项目成员和项目模型策略
- 只有管理员可以创建接入节点、聚合模型和路由绑定关系
- 只有管理员可以配置聚合模型节点的授权范围
- 普通用户只能查看自己所属项目、项目关联聚合模型、平台级聚合模型和关联 Key 信息
- 普通用户默认不具备创建 API Key 的权限
- 普通用户默认不具备修改聚合模型和路由策略的权限

## 10. 部署建议

一期建议采用简单、稳定、易交付的部署方式：

1. 前端静态站点部署
2. 后端 FastAPI 服务部署
3. PostgreSQL 作为主数据库
4. Redis 作为缓存、限流和短期状态存储
5. Nginx 作为统一入口

后续如果调用规模增长，可以逐步拆分为：

- 管理 API 服务
- 模型网关服务
- 审计与统计异步处理服务

## 11. 一期 MVP 范围

建议一期控制在可闭环范围内，优先完成：

1. 用户登录与基础权限
2. 组织管理
3. 项目管理
4. 个人 Key 与项目 Key 管理
5. 模型接入管理与模型出口聚合管理分离
6. OpenAI 兼容网关入口
7. 节点级并发、请求、token 限流
8. 调用日志查询
9. 平台总览首页
10. 基础告警能力

## 13. 推荐实施顺序

建议按以下顺序推进：

1. 后端基础框架与工程化能力

4. 单个供应商与节点接入打通
5. 节点级限流与日志记录
6. 前端管理控制台
7. 多供应商路由、告警与分析能力
