# AI Gateway 需求对齐版设计

## 1. 说明

本文件基于当前已沉淀的架构设计与数据库设计，并结合需求文档中的功能列表重新整理，目标是让设计更贴近实际产品需求、运营诉求和企业级治理场景。

本次整理重点对齐了以下需求方向：

- 平台总览与运营看板
- 模型管理与节点治理
- 用户、组织、项目、凭证管理
- 安全策略
- 日志审计与告警通知
- MCP 网关能力
- 非功能性与企业级能力

## 2. 需求归类后的产品结构

结合需求表，整个系统建议拆成 8 个一级产品域。

### 2.1 平台总览

目标是让管理员和运营人员快速看到平台整体运行状态。

建议首页看板包含：

- 平台总调用量
- 总 token 消耗
- API Key 数量
- 模型数量
- 节点数量
- 项目数量
- 组织数量
- 各供应商调用占比
- 各模型调用趋势
- 项目 / API Key / 用户用量排行
- 节点异常与模型告警信息

设计建议：

- 首页聚合数据不要直接扫明细表，建议通过日聚合表和小时聚合表生成
- 平台总览分成三类卡片：
  - 总量卡片
  - 趋势图卡片
  - 告警与异常卡片

## 2.2 模型管理

从需求文档看，模型管理不是简单的模型列表，而是“模型能力管理 + 节点治理 + 调度策略”的组合。

建议拆成 5 个子模块：

1. 供应商管理
2. 模型目录管理
3. 节点管理
4. 路由与聚合策略
5. 在线调试与效果验证

### 2.2.1 供应商管理

职责：

- 管理公有云厂商、自建推理服务、代理网关等接入源
- 支持不同厂商的认证方式、基础地址、区域配置
- 支持供应商健康状态查看

### 2.2.2 模型目录管理

职责：

- 统一维护平台侧模型名
- 维护供应商模型映射
- 定义模型能力类型
- 管理模型可见性、状态、价格、上下文能力

模型能力类型建议标准化为：

- `llm`
- `vlm`
- `embedding`
- `rerank`
- `ocr`
- `text_to_image`

### 2.2.3 节点管理

这是需求表里最重要的一块。

节点不是抽象模型，而是真正承载流量的接入点。每个节点都需要可治理、可限流、可观测。

节点建议具备的核心属性：

- 所属供应商
- 所属模型
- 节点地址
- 区域 / 集群 / 环境
- 启用状态
- 健康状态
- 权重
- 优先级
- 最大并发数
- 每秒请求上限
- 每分钟请求上限
- 每分钟 token 上限
- 每日 token 上限
- 超时配置
- 熔断状态

### 2.2.4 路由与聚合策略

结合需求文档，模型管理需要支持：

- 多节点聚合
- 模型别名
- 权重路由
- 优先级路由
- fallback
- 节点摘除
- 项目级模型策略

推荐设计：

- 平台层定义统一模型
- 项目层配置“允许调用哪些模型”
- 路由层再决定“命中哪个节点”
- 节点层执行最终限流、熔断和转发

### 2.2.5 在线调试与效果验证

需求里明显希望具备调试和测试能力，建议在模型管理中内置调试台。

建议支持：

- 单模型调试
- 多节点对比调试
- Prompt 调试
- 参数调试
- 返回结果对比
- 耗时与 token 对比

## 2.3 用户、组织、项目管理

这部分建议维持“组织 -> 项目 -> 成员 / Key”的多租户结构。

### 2.3.1 用户管理

职责：

- 平台用户管理
- 登录与身份认证
- 用户状态管理
- 用户个人 Key 查看
- 用户个人用量统计

### 2.3.2 组织管理

职责：

- 组织创建与禁用
- 组织成员管理
- 组织角色管理
- 组织资源边界隔离

### 2.3.3 项目管理

职责：

- 项目创建与配置
- 项目成员管理
- 项目模型范围控制
- 项目 API Key 管理
- 项目用量统计

建议项目成为以下能力的核心边界：

- 访问权限边界
- 凭证归属边界
- 模型可见范围边界
- 配额与限流边界
- 日志查询边界

## 2.4 凭证管理

从需求表来看，凭证管理需要独立成域，不能只作为项目的附属功能。

建议凭证管理分成两类：

1. 个人 API Key
2. 项目 API Key

每个 Key 需要支持：

- 创建
- 启用 / 禁用
- 轮换
- 过期时间
- 访问模型范围
- 绑定节点范围
- IP 白名单
- 调用额度限制
- 最近使用记录

设计建议：

- 明文 Key 只展示一次
- Key 级限流与项目级限流叠加生效
- Key 级日志要能追溯到调用来源、目标模型、目标节点

## 2.5 安全策略

需求文档里安全项比较多，这意味着网关不能只做转发，还要有治理与防护能力。

建议安全策略拆成 4 层：

### 2.5.1 访问安全

- 鉴权校验
- Key 状态校验
- IP 白名单
- 组织 / 项目隔离

### 2.5.2 内容安全

- 敏感词检测
- Prompt 拦截
- 输出内容拦截
- 黑白名单规则

### 2.5.3 资源安全

- 请求限流
- token 限流
- 节点并发限制
- 配额控制
- 熔断与降级

### 2.5.4 配置安全

- 供应商密钥加密存储
- 审计变更记录
- 高危操作留痕

## 2.6 看板分析

从需求文档可以看出，除了首页总览，还需要更细的分析能力。

建议看板分析至少分成 4 类：

1. 用量分析
   - 按组织
   - 按项目
   - 按 Key
   - 按用户
   - 按模型
   - 按节点

2. 成本分析
   - token 成本趋势
   - 供应商成本占比
   - 模型成本排行

3. 性能分析
   - 请求耗时
   - TTFT
   - TPOT
   - token/s
   - 错误率

4. 质量分析
   - 成功率
   - fallback 触发次数
   - 节点健康波动

## 2.7 日志管理与审计

需求文档里对日志能力要求比较重，这说明日志不只是排障工具，也是审计和运营工具。

建议日志域拆成三类：

### 2.7.1 网关调用日志

记录：

- 请求来源
- 命中的 Key
- 命中的项目
- 命中的模型
- 命中的节点
- 请求耗时
- 状态码
- 错误原因

### 2.7.2 管理行为审计日志

记录：

- 登录
- 创建 / 删除项目
- 创建 / 轮换 Key
- 修改模型策略
- 修改节点状态

### 2.7.3 安全审计日志

记录：

- 敏感词命中
- 拦截规则触发
- 访问异常
- 限流触发
- 熔断触发

## 2.8 预警通知

这部分建议做成独立能力中心，而不是日志页的一部分。

告警触发源建议包括：

- 节点异常
- 供应商异常
- 错误率升高
- token 使用超阈值
- 项目额度接近上限
- Key 异常调用
- 安全规则命中

通知方式建议至少支持：

- 邮件
- Webhook
- 企业 IM

## 2.9 MCP 网关

需求表里已经明确提到了 MCP 网关，这一块建议作为可选增强模块设计。

建议职责包括：

- MCP Server 注册
- MCP Tool 元数据管理
- 调用认证
- 调用审计
- 请求转发
- 工具可见范围控制

如果后续要支持 HTTP / SSE / Stdio 等不同接入方式，建议在架构上把 MCP 网关单独作为一个模块，而不是塞进普通模型网关逻辑里。

## 3. 面向需求的后端模块重组建议

结合需求表，后端模块建议从原先的技术分层，再向业务域靠拢，变成下面这组核心模块：

- `overview`：平台总览与聚合统计
- `auth`：登录、身份与权限
- `organization`
- `project`
- `credential`：统一管理个人 Key 与项目 Key
- `provider`
- `model`
- `node`
- `routing`：模型聚合、路由、fallback、权重策略
- `gateway`
- `quota`
- `safety`
- `audit`
- `alert`
- `mcp`
- `analytics`

这里建议把原来的 `apikey` 模块升级成 `credential`，因为需求表中的凭证管理明显不只是一把 Key 的 CRUD。

建议前端后台主菜单改成以下结构：

1. 总览
2. 模型管理
   - 供应商管理
   - 模型目录
   - 节点管理
   - 路由策略
   - 在线调试
3. 用户与权限
   - 用户管理
   - 组织管理
   - 项目管理
4. 凭证管理
   - 个人 Key
   - 项目 Key
5. 安全中心
   - 安全策略
   - 敏感词规则
   - IP 规则
6. 分析看板
   - 用量分析
   - 成本分析
   - 性能分析
7. 日志中心
   - 调用日志
   - 审计日志

## 5. 对数据库设计的补充要求

结合需求表，数据库除了现有设计，还要特别注意以下几类聚合和审计数据：

### 5.1 聚合统计表

建议补充：

- 平台日聚合表
- 项目日聚合表
- Key 日聚合表
- 模型日聚合表
- 节点日聚合表

这些表用于支撑：

- 首页总览
- 趋势图
- 排行榜
- 告警阈值判断

### 5.2 指标维度扩展

对于 LLM/VLM 节点，建议重点记录：

- 输入 token
- 输出 token
- 总 token
- TTFT
- TPOT
- token/s

对于 OCR / 文生图等非 token 主导模型，建议扩展记录：

- OCR 页数
- 图片张数
- 文件大小
- 处理耗时

### 5.3 审计对象扩展

建议后续补充这些表：

- `alert_rules`
- `alert_events`
- `audit_events`
- `security_rules`
- `security_events`
- `mcp_servers`
- `mcp_tools`
- `mcp_call_logs`

## 6. 一期 MVP 重新收束

如果严格按需求表全做，一期会偏大。建议重新收束成以下必做范围：

### 6.1 一期必做

- 用户 / 组织 / 项目基础管理
- 个人 Key 与项目 Key 管理
- 模型、供应商、节点三层管理
- 节点并发 / request / token 限流
- 基础路由策略
- 调用日志
- 平台总览首页
- 基础告警

### 6.2 一期可延后

- 多节点对比调试台
- 高级安全策略
- MCP 网关全能力
- 复杂成本中心
- 全量性能分析看板

## 7. 当前设计结论

结合这份需求文档，项目设计需要明确升级为：

1. 不只是“模型网关”，而是“企业级模型治理平台”
2. 不只是“模型管理”，而是“供应商 + 模型 + 节点 + 路由”的完整治理体系
3. 不只是“API Key 管理”，而是“个人凭证 + 项目凭证 + 策略控制 + 审计”
4. 不只是“调用日志”，而是“调用日志 + 安全日志 + 管理审计 + 告警联动”
5. 不只是“LLM 网关”，而是面向 `llm`、`vlm`、`embedding`、`rerank`、`ocr`、`text_to_image` 的统一接入平台

## 8. 下一步建议

基于这版需求对齐设计，最值得继续细化的是三份文档：

1. 管理面 API 设计
2. 节点调度与限流设计
3. 看板指标与聚合表设计

这三份会直接决定后端核心实现和前端页面拆分方式。
