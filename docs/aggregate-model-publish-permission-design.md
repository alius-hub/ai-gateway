# AI Gateway 聚合模型发布与权限解析设计

## 1. 说明

本文件用于补充聚合模型在平台内的发布、授权、可见性、可用性和管理权限设计。

聚合模型在完成节点绑定之后，还需要通过权限管理决定“可以下发给谁使用”。否则即使模型已经存在，也无法安全地被项目、个人或组织使用。

本设计重点回答以下问题：

- 聚合模型如何发布
- 聚合模型可以授权给哪些对象
- 可见、可用、可管理三类权限如何区分
- 权限冲突时按什么顺序解析
- 权限管理与项目策略之间如何衔接

## 2. 设计目标

需要同时满足以下场景：

1. 平台级聚合模型对多个组织开放
2. 某个聚合模型只发给指定项目
3. 某个聚合模型只发给指定个人用户
4. 某个聚合模型按自定义用户组批量发放
5. 同一个模型可以对不同对象仅开放“可见”或“可用”权限
6. 项目拿到模型后，可以对路由和限流做项目级覆盖

## 3. 核心概念

建议将模型治理拆成四层：

1. 聚合模型
   - 定义对外模型名称
   - 例如 `chat-pro`、`embedding-unified`

2. 聚合模型节点绑定
   - 定义底层节点池
   - 负责主备、灰度、权重、能力标签

3. 聚合模型权限管理
   - 定义这个模型能下发给谁
   - 负责发布和授权

4. 项目模型策略
   - 定义项目拿到模型以后，如何覆盖默认路由和限流

## 4. 授权对象设计

建议统一支持四类授权对象：

### 4.1 组织

适用场景：

- 某个模型提供给整个组织内使用
- 组织内多个项目共享一组聚合模型

### 4.2 项目

适用场景：

- 某个模型只发给指定项目
- 用于精细化项目隔离

### 4.3 用户

适用场景：

- 某个聚合模型只开放给指定个人
- 用于内测、白名单或特殊能力试用

### 4.4 用户组

适用场景：

- 按团队、部门、角色批量授权
- 比逐个用户授权更适合企业管理

## 5. 权限类型设计

建议统一为三类权限：

### 5.1 `visible`

表示“可以看到”。

拥有该权限时：

- 用户能在控制台看见这个聚合模型
- 用户能在模型列表中看见这个聚合模型

但不代表一定能调用。

### 5.2 `usable`

表示“可以使用”。

拥有该权限时：

- 对应对象可以在实际请求中调用该聚合模型

注意：

- `usable` 隐含 `visible`
- 但建议存储时仍允许显式配置，便于审计

### 5.3 `manageable`

表示“可以管理”。

拥有该权限时：

- 可修改聚合模型授权配置
- 可维护项目策略
- 可维护绑定关系

一期建议：

- `manageable` 只给管理员
- 普通用户默认不应具备

## 6. 发布范围设计

建议聚合模型支持以下发布范围：

### 6.1 平台级发布

适合：

- 平台通用模型
- 默认基础模型

规则建议：

- 可以发布给组织
- 可以发布给项目
- 可以发布给用户
- 可以发布给用户组

### 6.2 组织级发布

适合：

- 某组织内部专用模型
- 组织自建私有化能力

规则建议：

- 只能发布给本组织下的项目和用户；用户组是独立对象，若组织级授权给用户组，实际使用者仍需单独具备该组织的访问权限

### 6.3 项目级发布

适合：

- 某项目独享模型
- 某项目灰度试点模型

规则建议：

- 直接授权给项目
- 也可授权给项目内指定用户或用户组

## 7. 权限解析顺序

建议采用“越具体越优先”的解析顺序。

推荐顺序：

1. 用户直接授权
2. 用户组授权
3. 项目授权
4. 组织授权
5. 平台默认授权

解析原则：

- 先找最具体的授权
- 再逐步回退到更大的范围

## 8. 冲突处理规则

建议定义如下规则：

### 8.1 优先级

优先级从高到低：

```text
user > user_group > project > organization > platform_default
```

### 8.2 权限合并规则

建议采用“取最大有效权限”的方式：

```text
manageable > usable > visible
```

例如：

- 项目有 `usable`
- 用户组只有 `visible`

最终按 `usable` 生效。

### 8.3 禁用优先

若存在明确禁用记录，建议优先于低层级放行记录。

后续可扩展字段：

- `effect_type = allow | deny`

一期如果不做显式拒绝，也建议先预留设计。

## 9. 权限解析结果

建议每次登录或刷新权限时，最终解析出三类结果：

1. 当前用户可见的聚合模型集合
2. 当前用户可用的聚合模型集合
3. 当前用户可管理的聚合模型集合

其中：

- 控制台模型列表取“可见集合”
- 网关 `/v1/models` 取“可用集合”
- 管理台配置入口取“可管理集合”

## 10. 与项目策略的关系

这里建议明确边界：

### 10.1 权限管理先于项目策略

先判断这个模型是否授权给该项目或用户，再决定项目策略是否生效。

也就是说：

- 没有授权，不进入项目策略阶段
- 有授权，才读取项目策略

### 10.2 项目策略只做覆盖，不做授权

项目策略负责：

- 是否启用
- 是否固定节点
- 是否覆盖灰度
- 是否覆盖限流
- 是否覆盖能力要求

项目策略不负责：

- 决定谁能看见模型
- 决定谁能使用模型

这些应由聚合模型权限管理决定。

## 12. 示例

以 `chat-pro` 为例：

### 12.1 基础模型

- `chat-pro`
- 类型：`llm`

### 12.2 节点绑定

- A：OpenAI，`stable`
- B：DeepSeek，`stable`
- C：私有化 Qwen，`backup`
- D：新供应商，`canary`

### 12.3 权限下发

可以配置成：

- 授权给组织 `org-a`：`visible`
- 授权给项目 `project-x`：`usable`
- 授权给用户组 `research-team`：`usable`
- 授权给用户 `u123`：`manageable`

最终效果：

- `org-a` 用户默认能看见 `chat-pro`
- `project-x` 内可实际调用 `chat-pro`
- `research-team` 成员即使不在 `project-x`，也可获得额外可用权限
- 用户 `u123` 可以管理该模型相关配置

## 13. 一期推荐实现范围

一期建议优先支持：

1. 组织授权
2. 项目授权
3. 用户授权
4. 用户组授权
5. `visible` / `usable`

一期可以先不开放：

1. 显式 `deny`
2. 复杂权限冲突工作流
3. 自动继承规则编辑器

`manageable` 可以在实现上先只给管理员，不必做复杂授权编辑器。

## 14. 查询建议

建议后台至少提供以下能力：

- 查询某个聚合模型发给了哪些对象
- 查询某个项目可见哪些聚合模型
- 查询某个用户最终可见/可用哪些聚合模型
- 查询某个用户组继承了哪些模型权限
